# PAWSON AI 公开开发日志 · 日更流程

**简体中文** · [English](daily-update-workflow.en.md)

这套流程规定 PAWSON AI 如何每天从私人源码项目中提炼可以公开的开发进展。目标是持续讲清产品为什么变化、当天真实完成了什么、怎样验证，以及仍有什么限制，同时保护源码、凭证、客户和内部系统。

## 更新节奏

- 以 Asia/Shanghai 自然日为准，每天完成一次公开检查和更新。
- 当天有多个开发节点时，合并为一篇日记，围绕一个清晰主题组织内容。
- 当天没有达到可公开、可验证的节点时，发布简短状态说明，写明“仍在进行”“仅内部工作”或“暂无新增验证结果”，不虚构进展。
- 重大版本、路线变化或重要验证结果出现时，同步更新首页、开发历程、路线图或版本记录。
- 中英文内容在同一次发布中完成，不能只更新一种语言。

## 每日输入

日更首先读取事实，不从印象或计划倒推结果。可使用的输入包括：

1. 私人源码仓库当天的提交记录、当前分支和工作树状态。
2. 已完成任务的验收说明、测试、构建、Smoke 和人工验证结果。
3. 产品界面、真实输出文件和经过确认的阶段截图。
4. 已记录的技术取舍、已知限制和下一步方向。
5. 上一篇公开日记，避免重复讲述或把旧结果写成当天进展。

未提交修改可以作为“正在进行”的证据，但不能被写成已经交付。界面提示、占位结果、本地缓存和计划清单也不能单独证明成功。

## 第一步：建立当天事实清单

先把材料分成四类：

| 分类 | 可以写什么 | 写作要求 |
| --- | --- | --- |
| 已完成 | 已落地且有证据的产品变化 | 使用过去时，写清用户价值 |
| 已验证 | 测试、构建、真实文件或人工验收结果 | 给出可公开的数量、范围和边界 |
| 进行中 | 已开始但尚未完成的工作 | 明确标记，不写成结果 |
| 已知限制 | 失败项、外部依赖和暂未解决的问题 | 说明影响，不隐藏失败 |

如果证据互相冲突，以可复核的代码、文件、测试输出和远端状态为准。无法确认的内容写入“待验证”，或者不公开。

## 第二步：提炼公开故事

每天选择一个能让外部读者理解的主题，而不是罗列内部文件名。正文通常回答六个问题：

1. 今天为什么做这件事？
2. 用户此前遇到了什么问题？
3. 今天真正完成或确认了什么？
4. 做出了哪些产品或工程取舍？
5. 有什么验证证据和真实边界？
6. 下一步准备验证什么？

允许写产品能力、用户体验、阶段截图、公开测试数字和不具复刻性的设计思路。避免逐条复制 Git 提交，因为提交信息常含内部模块名，外部读者也难以理解其价值。

## 第三步：执行脱敏检查

以下内容禁止进入公开仓库：

- 源代码、完整代码差异、完整系统架构和可直接复刻的关键算法。
- API Key、Token、Cookie、Password、密钥文件和真实测试凭证。
- Provider 地址、内部接口、服务器 IP、后台地址、端口和部署配置。
- 数据库结构、迁移细节、真实业务数据和内部账务规则。
- 客户名称、用户账号、聊天内容、订单、联系方式和个人信息。
- 浏览器 Profile、绝对本地路径、内部仓库地址和未公开合作方信息。
- 完整系统提示词、安全绕过方式和内部风控细节。

无法判断是否敏感时，不发布该细节。可以改写为产品影响、验证结论或抽象后的实现方向。

## 第四步：处理项目图片

图片只用于解释真实产品变化，并按以下顺序处理：

1. 选择与当天主题直接相关的界面、输出或前后对比。
2. 检查窗口标题、浏览器标签、账号头像、通知、路径、文件名和后台地址。
3. 裁掉无关桌面区域，遮盖不能公开的信息。
4. 清理 EXIF、XMP、IPTC、GPS 和软件路径等元数据。
5. 使用通用文件名，例如 `2026-09-agent-workspace.png`。
6. 在中英文正文中添加准确的替代文本和简短图注。

图片不能作为完成证据的唯一来源。涉及外部服务时，还要有运行状态、文件或日志等可复核结果。

## 第五步：编写中英文日记

每个日期创建一对文件：

```text
updates/YYYY-MM-DD.md
updates/YYYY-MM-DD.en.md
```

中文和英文页面顶部互相链接。两份内容表达相同事实、数字、限制和下一步，英文版按英文读者习惯自然改写，不机械逐句翻译。

标准结构沿用 [中文模板](../updates/TEMPLATE.md) 和 [English template](../updates/TEMPLATE_EN.md)：

- 为什么做
- 这次完成
- 关键取舍
- 验证证据
- 已知限制或仍待验证
- 下一步

标题要描述变化，例如“Agent 开始处理文件和长任务”，避免使用“今日更新”“继续优化”等缺少信息的标题。

## 第六步：更新导航和长期文档

每篇日记完成后，至少更新：

- `updates/README.md`：中文日期索引。
- `updates/README_EN.md`：英文日期索引。
- `README.md` 与 `README_EN.md`：首页“最新进展”链接和当前状态。

出现以下情况时再更新对应长期文档：

| 触发条件 | 更新位置 |
| --- | --- |
| 产品主线、关键取舍或阶段故事发生变化 | `docs/development-history.md` 及英文版 |
| 目标优先级或公开计划变化 | `ROADMAP.md` 及英文版 |
| 用户可感知的变化值得快速查阅 | `CHANGELOG.md` 及英文版 |
| 形成明确交付版本 | `releases/` 中英文版本页 |
| 新增安全可公开的界面素材 | `screenshots/` 图片集索引 |

## 第七步：发布前验证

发布前必须完成以下检查：

- 日期、数字、版本号和完成状态与证据一致。
- 中文和英文页面事实一致，并能互相跳转。
- 所有相对链接、图片路径和目录索引有效。
- Markdown 格式检查通过，没有破损表格或空链接。
- 文本未出现密钥格式、凭证、内部地址、客户数据或绝对路径。
- 图片已完成人工画面检查和元数据检查。
- Git 差异只包含本次公开日记所需文件。

任一检查无法通过时，保留本地草稿，不推送半成品。

## 第八步：提交、发布和远端确认

推荐提交信息：

```text
docs: publish YYYY-MM-DD development journal
```

推送公开仓库后，还要确认：

1. GitHub `main` 已指向本次提交。
2. 中英文日记都能从目录进入。
3. 首页“最新进展”链接指向当天页面。
4. 图片可以显示，语言切换可以返回对应页面。
5. 本地分支与远端一致，工作树没有遗漏的临时发布文件。

只有远端确认完成后，才能宣布当天日记已经发布。网络失败或推送失败时，应保留本地提交并重试，不能把本地成功描述为公开发布成功。

## 每日完成标准

一轮日更只有同时满足以下条件才算完成：

- 真实：所有完成项都有证据，进行中和失败项没有被包装成成功。
- 安全：正文、链接和图片通过脱敏检查。
- 双语：中英文内容与导航同步。
- 可读：外部读者能理解问题、变化、影响和下一步。
- 可达：远端页面、图片和语言切换均已验证。

这套流程会随着项目继续演进，但“证据优先、敏感信息不公开、双语同步、远端确认后才算发布”四项原则保持不变。
