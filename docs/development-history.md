# 开发历程：从商品生产工具到本地优先的 AI 工作台

> 这是一篇持续更新的开发日记。最后更新：2026-09-10。

PAWSON AI 不是按一张完整蓝图一次完成的。它是在真实交付、失败恢复、产品取舍和持续验证中逐渐成形的。每一阶段都解决前一阶段暴露的问题，也重新定义下一步真正值得做的事。

这篇文章保留过程中的关键判断。它不会公开私人源码、完整系统结构、内部接口、供应商配置或安全实现。

## 起点：先把商品图片生产真正跑通

最初的问题很具体：跨境商品内容生产需要在生成、抠图、裁剪、放大、模板套图和导出之间反复切换。单个 AI 功能并不稀缺，真正费时间的是素材搬运、参数重复填写、结果丢失，以及不知道一次任务究竟有没有成功。

第一阶段没有急着做一个万能助手，而是先完成可交付的 Windows 工作流。到 2026-07-25，早期版本已经能够处理文字生成图片、参考图生成、本地抠图、精确裁剪、图片放大和模板展示，并形成安装版与便携版交付物。

这一阶段建立了后来一直坚持的原则：界面显示“完成”不算完成。文件必须真实存在，尺寸和格式要能检查，任务失败不能覆盖已有结果，高风险内容必须保留人工复核位置。

早期交付基线包括 51 个测试文件、152 项自动化测试，以及安装包中的实际图片处理验证。它并不代表产品成熟，却证明了最核心的一条生产链能够从输入走到真实文件。

## 2026-07-27 至 07-28：从本地工具走向商业客户端

当工具开始具备交付能力，新的问题随之出现：账号如何登录，套餐和额度如何管理，桌面客户端如何连接统一服务，更新如何发到用户手里，支付结果又如何避免仅凭前端状态判断。

这两天的工作集中在商业基础设施。产品加入账户与设备边界、控制中心、正式支付配置、支付结果验证、模型能力发现和桌面版本发布流程。随后发布的 1.0.6 修正了打包客户端的默认连接路径，使正式客户端能够使用云端控制能力。

这个阶段最大的变化不是多了几个后台页面，而是开始把“本机看起来能用”和“服务端确认有效”分开。付款、积分、权限和远程任务都必须以可信服务端状态为准。

## 2026-07-30 至 08-02：工具不能继续各自为战

随着图片能力增加，用户会在不同页面之间迷失：当前处理的是哪张图，哪个结果属于哪个任务，生成后的图片怎样继续抠图或套模板，连接中断后还剩下什么。

这一轮把分散功能收束成统一生产工作区。任务选择、生产步骤、结果展示和继续加工开始共享同一套状态。结果可以从一个步骤安全送往下一个步骤，重复点击不会重复触发同一操作，连接恢复后也能重新核对真实任务状态。

8 月初，工作区进一步转向“项目中心”思路。素材、参数、过程和结果不再只是某个页面的临时状态，而应当属于一个可以继续打开的项目。1.1.x 内部测试版本就是在这一时期形成的。

## 2026-08-03 至 08-20：从生产页面扩展到经营工作台

商品内容只是经营链路的一部分。图片做好以后，团队仍然需要回答：哪些商品值得继续投入，广告、退款和成本发生了什么变化，分析结果怎样变成行动，行动完成后如何复查。

8 月中旬，PAWSON 开始形成跨境经营工作区、报告中心、任务视图和全局助手的雏形。这里遇到的难题不再只是“调用哪个模型”，而是怎样让建议基于可信数据，怎样区分事实和推断，怎样在长任务中保存上下文，以及传输失败后如何恢复。

这一阶段也推动了产品语言的变化：AI 不应只是悬浮在页面上的聊天框，而应理解用户当前所在的业务区域，读取经过授权的上下文，并把结果交付成能继续使用的内容。

## 2026-08-21：Agent MVP 成为新的主线

到 8 月 21 日，PAWSON Agent 的 MVP 基线形成。它具备持续对话、任务状态、专业能力选择和基础恢复能力，产品开始从“多个带 AI 的工具”转向“一个能使用多种工具的智能工作台”。

这次转向也暴露了新的风险：如果 Agent 只会生成一段漂亮回答，却不能验证文件、等待审批、处理失败或保留任务状态，它仍然无法承担真实工作。因此后续开发开始围绕可观察、可停止、可恢复和可验证展开。

## 2026-08-22 至 08-26：让数据、知识和采集成为可信上下文

接下来的几天建立了多任务基础、网页采集、数据资产和知识库链路。产品能够把采集结果保存为可追溯的数据资产，再交给知识库、经营模块和 Agent 使用。

数据进入系统并不意味着它天然可信。PAWSON 需要保留来源、时间范围和处理状态；当信息不完整时，应告诉用户缺少什么，而不是从旧对话里拼凑一个看似合理的答案。

同一时期，商品详情能力也开始从一次性生成转为可编辑项目。视觉草稿、商品信息和生成结果能够围绕项目继续积累，为后来的项目库打下基础。

## 2026-08-27 至 08-30：统一工作区、专家与项目库

当模块越来越多，导航和上下文再次成为主要摩擦。8 月底完成了工作区整合、专家创建流程、商品详情项目库和全局助手体验。

商品详情项目能够保存、继续编辑、复制、导入导出和恢复草稿。全局助手能够理解当前页面，但不替用户擅自执行高影响动作。专家系统开始把视觉诊断、经营分析和文档交付沉淀为可维护的方法，而不是把所有任务塞进一段越来越长的提示词。

这一时期的核心判断是：专业化不等于堆叠角色名称。专家必须有明确边界、稳定方法和可验证输出；简单任务不应为了展示“多智能体”而制造额外复杂度。

## 2026-09-01：Agent 开始处理真实工作

9 月 1 日是一次密集的能力跃迁。Agent 获得受控命令执行、长任务状态、文件产物、办公文档与表格能力，以及外部 Skill 的发现和加载入口。

这带来三个必须同时解决的问题：命令执行要经过权限边界，长任务中断后要保留有效结果，生成文件要经过真实存在性检查。产品因此加入审批、恢复、产物卡片和安全工作区边界，让“我已经生成文件”能够落到用户真正可以打开的文件上。

## 2026-09-02 至 09-06：换上正式运行时，形成综合 Agent 里程碑

9 月初，NEW PAWSON AI 接入正式 Agent 运行时，并逐步完成线程恢复、任务内补充输入、停止、工具活动、错误呈现、图片与文件输入等体验。

随后，视觉诊断、经营分析和文档交付三类专家能力进入统一工作区。它们分别负责可见证据、经营口径和正式交付，但最后仍由同一个主任务形成一致答案。

到 2026-09-06，这些能力汇合成一个明确里程碑：PAWSON 不再只是工具集合，而是开始具备统一 Agent 入口、业务上下文、专业方法、可信执行和文件交付的综合工作台。

当日验证基线为 365 个测试文件、2342 项测试通过，生产构建通过。真实体验仍然保留人工验收，因为自动测试无法替代模型延迟、图片质量和操作手感。

## 2026-09-07 至 09-09：架构收敛与 2.0 阶段

里程碑之后，工作重点转向收敛。项目重新梳理模块边界，建立更安全的 AI 网关链路，并把模型选择绑定到具体会话。旧 Agent 路径逐步退出，新能力统一进入 NEW PAWSON AI 主线。

2026-09-09，桌面产品升级为“派笙 AI 中台 2.0”。这一版本统一了桌面端、控制中心、报告和采集扩展的品牌，同时保留既有账户、积分、数据目录和更新兼容性。

2.0 不是终点。多模型目录、短期访问凭证和每个会话的模型选择已经形成代码与测试基线，但真实服务可用性仍需在正确配置的环境中验收。未发生的真实调用不会被写成已成功。

## 2026-09-10：开始验证商业接入的最小闭环

当前工作进入 P0 验证阶段。重点是弄清一次真实 Agent 任务中会发生多少次模型请求，以及身份、重试、限流、取消、中断和用量记录如何对应。

这项工作先在隔离环境中进行，不调用付费模型，也不直接改动生产系统。只有把请求级行为测清楚，后续的订阅、钱包、计价和审计才有可靠基础。

每个得到真实验证的重要节点都会继续写进本文，同时在 `updates/` 中保留独立日期记录。更新遵循四条规则：

1. 只把实际完成或实际验证的内容写成结果。
2. 明确区分产品方向、代码基线和真实服务验收。
3. 记录关键取舍和问题，不公开可复刻的核心实现。
4. 不发布凭证、客户数据、内部地址、完整架构和安全配置。
